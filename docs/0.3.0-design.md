# MCA: Quests v0.3.0 — Phase 1 Design

This is the **Phase 1 deliverable** (design only — no feature code). It mirrors the canonical condition syntax extracted in Phase 0 and specifies the JSON schema for each new condition, the `McaCompat` method contracts, the evaluation/caching strategy, and the validation rules. **Hard STOP at the end — awaiting approval before Phase 2.**

All MCA API signatures below were verified with `javap` against `.bootstrap/mca.jar` (MCA Reborn `7.6.20+1.20.1`). All new conditions use the **`mcaquests:`** namespace (house style), evaluate **server-side only**, and **fail safe** (default *not met* + `DEBUG` log) when MCA data is missing.

---

## 1. JSON schema per condition

Each condition mirrors the existing leaf style: `{ "type": "mcaquests:<id>", <fields> }`, and nests inside `all_of`/`any_of`/`not` with no extra work (composites recurse through the shared `ConditionTypes.CODEC`). All list/enum fields use validating codecs (the `TimeCondition.TimePeriod.CODEC` pattern) so unknown values fail at parse time.

### 1.1 `mcaquests:is_player_spouse`
Giver is married to the interacting player.
```json
{ "type": "mcaquests:is_player_spouse" }
```
No fields. → `McaCompat.isPlayerSpouse(player, villager)`.

### 1.2 `mcaquests:relationship_state`
Giver's MCA relationship state is in the list.
```json
{ "type": "mcaquests:relationship_state", "states": ["married_to_player", "engaged"] }
```
- `states`: required, non-empty list. Accepted: `single`, `promised`, `engaged`, `married_to_villager`, `married_to_player`, `widow`.

### 1.3 `mcaquests:is_family_member`
Giver is a relative of the player (MCA family tree).
```json
{ "type": "mcaquests:is_family_member", "relation": "child" }
```
- `relation`: optional, default `any`. Accepted: `any`, `parent`, `child`, `sibling`, `grandparent`.

### 1.4 `mcaquests:age_group`
Giver's MCA age state is in the list.
```json
{ "type": "mcaquests:age_group", "groups": ["adult"] }
```
- `groups`: required, non-empty list. Accepted: `baby`, `toddler`, `child`, `teen`, `adult`. **`elder` is not an MCA state — deferred/unavailable.**

### 1.5 `mcaquests:personality`
Giver's MCA personality is in the list.
```json
{ "type": "mcaquests:personality", "personalities": ["friendly", "peppy"] }
```
- `personalities`: required, non-empty list. Accepted (13): `athletic`, `confident`, `friendly`, `flirty`, `witty`, `shy`, `gloomy`, `sensitive`, `greedy`, `odd`, `lazy`, `grumpy`, `peppy`.

### 1.6 `mcaquests:mood`
Giver's mood value within range and/or named mood in list. At least one of the fields must be present.
```json
{ "type": "mcaquests:mood", "min": 0, "moods": ["happy"] }
```
- `min` / `max`: optional ints (mood value; MCA range ~ `MoodGroup.NORMAL_MIN_LEVEL..MAX_LEVEL`).
- `moods`: optional list of mood names (lowercased `Mood.getName()`). *Mood names are data-driven in MCA; in lenient mode an unmatched name simply never matches rather than failing parse — documented as such.*

### 1.7 `mcaquests:village_member`
Giver belongs to a home village.
```json
{ "type": "mcaquests:village_member", "value": true }
```
- `value`: optional bool, default `true`. → `McaCompat.hasHomeVillage(villager)`.

### 1.8 `mcaquests:has_home`
Giver has an assigned home position.
```json
{ "type": "mcaquests:has_home", "value": true }
```
- `value`: optional bool, default `true`. → `McaCompat.hasHome(villager)`.

### 1.9 `mcaquests:health_below`
Giver's health fraction is below a threshold.
```json
{ "type": "mcaquests:health_below", "threshold": 0.5 }
```
- `threshold`: required double in `(0,1]`. True when `getHealth()/getMaxHealth() < threshold`.

### 1.10 `mcaquests:infected`
Giver is zombie-infected past a progress threshold.
```json
{ "type": "mcaquests:infected", "min_progress": 0.01 }
```
- `min_progress`: optional double, default `0.0` exclusive (any progress `> 0`). True when `getInfectionProgress() >= min_progress` (and `> 0` when default).

### 1.11 `mcaquests:related_villager_status`
Giver has ≥1 relative of `relation` whose status matches.
```json
{ "type": "mcaquests:related_villager_status", "relation": "child", "status": "missing" }
```
- `relation`: required. Accepted: `spouse`, `parent`, `child`, `sibling`.
- `status`: required. Accepted: `alive`, `nearby`, `missing`, `dead`, `same_village`.

## 2. `McaCompat` method contracts

One method per data point. All reside in `compat/McaCompat.java`. **Every method:** guards `entity instanceof VillagerEntityMCA` (or `VillagerLike`/`LivingEntity` where broader), wraps MCA access in `try/catch`, returns the **safe default** below on non-MCA entity / null data / any throwable, and logs at `DEBUG` via `McaQuests.LOGGER` on the failure path. No method ever propagates an exception.

| Method | Returns | Safe default | MCA path |
|---|---|---|---|
| `isPlayerSpouse(ServerPlayer p, Entity e)` | `boolean` | `false` | `EntityRelationship.of(e)` → `isMarriedTo(p.getUUID())` (state `MARRIED_TO_PLAYER`) |
| `getRelationshipState(Entity e)` | `Optional<String>` | `empty` | `EntityRelationship.of(e).getRelationshipState().name()` lowercased |
| `isFamilyOfPlayer(ServerPlayer p, Entity e, String relation)` | `boolean` | `false` | `EntityRelationship.of(e).getFamilyEntry()` → `isRelative/isParent/isGrandParent/streamChildren/siblings` vs `p.getUUID()` |
| `getAgeStateName(Entity e)` | `Optional<String>` | `empty` | `VillagerLike.getAgeState().name()` lowercased |
| `getPersonalityName(Entity e)` | `Optional<String>` | `empty` | `getVillagerBrain().getPersonality().name()` lowercased |
| `getMoodValue(Entity e)` | `OptionalInt` | `empty` | `getVillagerBrain().getMoodValue()` |
| `getMoodName(Entity e)` | `Optional<String>` | `empty` | `getVillagerBrain().getMood().getName()` lowercased |
| `hasHomeVillage(Entity e)` | `boolean` | `false` | `getResidency().getHomeVillage().isPresent()` |
| `hasHome(Entity e)` | `boolean` | `false` | `getResidency().getHome().isPresent()` |
| `getHealthFraction(Entity e)` | `OptionalDouble` | `empty` | `LivingEntity.getHealth()/getMaxHealth()` |
| `getInfectionProgress(Entity e)` | `float` | `0f` | `VillagerEntityMCA.getInfectionProgress()` |
| `relativesWithStatus(ServerLevel lvl, Entity giver, String relation, String status)` | `boolean` | `false` | see below |

**`relativesWithStatus` algorithm** (the only non-trivial one):
1. Resolve the giver's `FamilyTreeNode` via `EntityRelationship.of(giver).getFamilyEntry()` (or `FamilyTree.get(lvl).getOrEmpty(giver.getUUID())`).
2. Collect candidate relative UUIDs by `relation`: `spouse`→`partner()`; `parent`→`streamParents()`; `child`→`streamChildren()`; `sibling`→`siblings()`.
3. For each candidate UUID, classify status:
   - `dead` → `FamilyTree.get(lvl).getOrEmpty(uuid)` exists and `isDeceased()`.
   - `alive` → resolvable as a living entity in `lvl` (`lvl.getEntity(uuid)` alive) OR in-tree and not deceased.
   - `nearby` → resolvable, living, within an interaction radius of the giver (reuse the `canPlayerInteract` distance constant).
   - `missing` → in family tree, not deceased, but `lvl.getEntity(uuid)` is null (unloaded/gone).
   - `same_village` → giver's `Village.getResidentsUUIDs()` contains the candidate UUID (via `getResidency().getHomeVillage()`).
4. Return `true` if **any** candidate matches the requested status.

This method is the only one that touches `FamilyTree`/`Village` server data; it is invoked **only** when a `related_villager_status` condition is present and its result is memoized on the snapshot (§3).

## 3. Evaluation & caching strategy

Per Phase 0: condition evaluation runs **only at eligibility-check time** (`QuestManager.eligibleOffers()` on menu-open and accept-revalidation) — **never per tick**. Default lean is sufficient; no persistent cache needed.

- **`compat/McaVillagerSnapshot.java`** — a new immutable holder built **once per `eligibleOffers()` pass** for the interacting villager. Eagerly captures the cheap per-villager fields: age-state name, personality name, mood value + name, infection progress, health fraction, relationship-state name, spouse UUID, `hasHomeVillage`/`hasHome` flags, and the `FamilyTreeNode` reference. Spouse-of-player and family-of-player are computed against the fixed interacting player and cached too.
- The heavier **`related_villager_status`** family resolution is computed lazily and **memoized on the snapshot** (keyed by `relation+status`), so repeated conditions in one pass don't re-walk the tree.
- **`QuestContext`** gains an `McaVillagerSnapshot mca()` accessor. `QuestManager.eligibleOffers()` builds the snapshot before the filter stream and threads the same instance into every `new QuestContext(player, villager, data, def.id(), snapshot)`. Net effect: a villager's MCA state is fetched **once per pass**, not once per condition (spec requirement).
- Existing `hearts()`/`profession()` helpers may also read from the snapshot for consistency (optional; non-breaking).

## 4. Validation rules (strict vs lenient)

The strict/lenient toggle is the **existing** `strictJsonValidation` config flag (`McaQuestsConfig.java:97`, default `false`), enforced by `QuestDataLoader`:

- **Parse-time (field validity).** Each enum-backed field (`states`, `relation`, `groups`, `personalities`, `status`, named `moods` where closed-set) uses a validating `Codec` that rejects unknown values with a clear `DataResult.error`. In **lenient** mode the loader skips the offending quest with a logged error (and `/mcaquests validate` lists it); in **strict** mode it is a hard error. Required-but-empty lists and out-of-range numbers (e.g. `threshold` outside `(0,1]`) are likewise rejected here.
- **Runtime safe-fail (data availability).** Independent of strict mode: when MCA is absent, the entity is not an MCA villager, or backing data is null/throws, the condition evaluates to **not met** and `McaCompat` emits a `DEBUG` log. The server never crashes on missing relationship/family data.

**Accepted value sets** (canonical, for docs + codecs):
- relationship states: `single, promised, engaged, married_to_villager, married_to_player, widow`
- family relation (to player): `any, parent, child, sibling, grandparent`
- related-villager relation: `spouse, parent, child, sibling`
- related-villager status: `alive, nearby, missing, dead, same_village`
- age groups: `baby, toddler, child, teen, adult` (elder = deferred)
- personalities: `athletic, confident, friendly, flirty, witty, shy, gloomy, sensitive, greedy, odd, lazy, grumpy, peppy`
